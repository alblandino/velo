Qué es Velo

Velo es un almacén clave-valor en memoria al que se accede por red. Lo construí desde cero en Node.js puro, sin una sola dependencia externa, tomando a Redis como modelo: habla el mismo protocolo (RESP) sobre TCP, entiende 23 de sus comandos y se puede usar desde su propio cliente o desde nc.

No pretende competir con Redis. Es una reimplementación de tamaño didáctico, unas 2.000 líneas repartidas en 40 módulos, donde cada pieza que normalmente se esconde detrás de una librería está escrita a mano y se puede leer en una tarde: el socket, el parser del protocolo, el despacho de comandos, el almacenamiento, la expiración de claves, el cliente interactivo, el parser de la línea de comandos e incluso el lector de .env.

  • Servidor TCP con el módulo net de Node.
  • Protocolo RESP y comandos inline (estilo telnet).
  • Parser incremental que tolera mensajes partidos y encadenados.
  • 23 comandos: strings, TTL y servidor.
  • 16 bases de datos lógicas con SELECT.
  • Expiración perezosa más un barrido periódico.
  • Cliente REPL con colores y modo de un solo comando.
  • Clean Architecture: dominio, aplicación e infraestructura.
  • Mensajes en español e inglés.
  • Recarga automática del servidor en desarrollo.
  • Persistencia en disco (no implementado).
  • Listas, hashes y sets (no implementado).

Marcado: funciona hoy. Sin marcar: no existe todavía; ver .

Por qué lo hice

Velo es un proyecto para aprender. La idea viene de Redis: una herramienta que casi todo el mundo usa como una caja negra (SET, GET, listo) y que, sin embargo, resuelve por dentro varios problemas clásicos de sistemas. La mejor forma de entender esos problemas era volver a resolverlos, sin atajos.

Por eso la regla principal del proyecto es cero dependencias. Cada vez que habría sido cómodo instalar algo (un parser de RESP, dotenv, un parser de argumentos, nodemon, una librería de i18n), la respuesta fue escribirlo. No porque sea mejor en producción, sino porque así no queda nada escondido.

Arquitectura

Velo sigue Clean Architecture: el código se ordena en capas y las dependencias solo apuntan hacia dentro. Un comando no sabe que existe TCP, ni RESP, ni la terminal; recibe un almacén y unos argumentos y devuelve un valor.

Puertos: lo que el dominio pide

El dominio declara dos contratos. IDataStore describe un almacén (get, set, del, keys, dbsize, flushAll, el barrido…) y InMemoryStore lo implementa con Map. Si mañana el almacén guardara en disco, los comandos no cambiarían. ICommandHandler describe la forma de un comando: un nombre estático y un método execute(store, args, db).

class GetCommand {
  static get nombre() { return 'GET'; }

  execute(store, args, db) {
    if (args.length !== 1) {
      return errorArgumentos('GET');
    }

    const entrada = store.get(db, args[0]);
    if (!entrada) return null;

    if (entrada.type !== TipoDato.STRING) {
      return errorTipo();
    }

    return entrada.value;
  }
}

Así es un comando completo. Valida, consulta el puerto y devuelve un valor JavaScript corriente: null, un string, un número, un array, { ok } o { err }. Traducir eso a bytes es trabajo de otra capa ().

El registro de comandos

CommandRegistry instancia los 23 handlers al arrancar y los guarda en un Map indexado por su nombre. Despachar un comando es una búsqueda O(1); añadir uno nuevo es crear un archivo y añadir una línea a la lista.

execute(nombre, args, store, db) {
  const handler = this._comandos.get(nombre);

  if (!handler) {
    return error('comandos.desconocido', { comando: nombre.toLowerCase() });
  }

  return handler.execute(store, args, db);
}

El protocolo RESP

RESP (REdis Serialization Protocol) es el idioma que hablan Redis y sus clientes. Es texto legible, pero cada dato lleva delante un byte que dice qué tipo es y, cuando hace falta, cuántos bytes ocupa. Cada línea termina en \r\n.

Tabla Los cinco tipos que usa Velo y el valor JavaScript que los produce.
PrefijoTipoEjemplo en el cableLo produce
+String simple+OK\r\n{ ok: 'OK' }
-Error-ERR comando desconocido: 'foo'\r\n{ err: '…' }
:Entero:11\r\nun number
$Bulk string$4\r\nhola\r\n · nulo: $-1\r\nun string · null
*Array*2\r\n$1\r\n1\r\n$-1\r\nun Array

Un comando, byte a byte

El cliente siempre envía un array de bulk strings. Así queda SET saludo hola fila a fila: a la izquierda lo que tecleas, a la derecha los bytes que lo representan. En total son 35 bytes.

Tabla SET saludo hola tecleado y en el cable, fila a fila.
TecleadoBytesSignifica
*3\r\nUn array de 3 elementos
SET$3\r\nBulk string de 3 bytes…
SET\r\n…que son SET
saludo$6\r\nBulk string de 6 bytes…
saludo\r\n…que son saludo
hola$4\r\nBulk string de 4 bytes…
hola\r\n…que son hola

Las longitudes son lo importante. Gracias a ellas el valor puede contener espacios o saltos de línea sin ambigüedad, y el parser sabe cuántos bytes esperar antes de dar un dato por completo. Fíjate en que la longitud se mide en bytes, no en caracteres: el serializador usa Buffer.byteLength, así que "ñ" viaja como $2\r\n.

Del valor a los bytes

Toda la traducción vive en un solo método de RespSerializer. Es el contrato entre la capa de aplicación y el protocolo:

static serializar(valor) {
  if (valor === null || valor === undefined) {
    return RespSerializer.nullBulk();          // $-1\r\n
  }
  if (typeof valor === 'object' && 'ok' in valor) {
    return RespSerializer.simpleString(valor.ok);   // +OK\r\n
  }
  if (typeof valor === 'object' && 'err' in valor) {
    return RespSerializer.error(valor.err);         // -ERR …\r\n
  }
  if (typeof valor === 'number') {
    return RespSerializer.integer(valor);           // :11\r\n
  }
  if (typeof valor === 'string') {
    return RespSerializer.bulkString(valor);        // $4\r\nhola\r\n
  }
  if (Array.isArray(valor)) {
    return RespSerializer.array(valor);             // *2\r\n…
  }
  return RespSerializer.bulkString(String(valor));
}

Comandos inline

Si el primer byte no es uno de los cinco prefijos, el parser trata la línea como un comando inline: la parte por espacios respetando comillas, como hace una shell. Por eso nc o telnet bastan para hablar con Velo ().

El parser incremental

TCP no entrega mensajes: entrega un flujo de bytes en trozos de tamaño arbitrario. Un comando puede llegar partido en dos eventos data, o tres comandos pueden llegar pegados en uno. El parser tiene que funcionar en ambos casos.

RespParser resuelve esto con una regla simple: acumula todo en un buffer e intenta leer un valor completo desde el principio. Cada función de lectura devuelve { valor, avance } si encontró un dato entero, o null si faltan bytes. Con null no se pierde nada; el parser simplemente espera al siguiente trozo.

_procesarBuffer() {
  while (this._buffer.length > 0) {
    const resultado = this._parsear(0);

    if (resultado === null) {
      break;                        // mensaje incompleto: esperar más datos
    }

    const { valor, avance } = resultado;
    this._buffer = this._buffer.slice(avance);   // descartar lo consumido
    this.emit('comando', valor);
  }
}

El bucle es lo que hace funcionar el pipelining: si en el buffer hay tres comandos completos, los emite los tres seguidos. La lectura de un bulk string muestra la otra mitad de la idea, comprobar que han llegado todos los bytes anunciados antes de leerlos:

_parsearBulkString(offset) {
  const longitudRes = this._parsearLinea(offset);
  if (!longitudRes) return null;

  const longitud = parseInt(longitudRes.valor, 10);
  if (longitud === -1) {
    return { valor: null, avance: longitudRes.avance };
  }

  const inicio = longitudRes.avance;
  const fin = inicio + longitud;

  if (this._buffer.length < fin + 2) return null;   // faltan bytes

  const contenido = this._buffer.toString('utf-8', inicio, fin);
  return { valor: contenido, avance: fin + 2 };
}

Comprobado con un socket real

Para verificarlo envié a un servidor Velo, en una sola escritura, un PING inline, un SET inline con comillas, un GET y un SET en RESP, seguidos de un segundo PING cortado a la mitad (…$4\r\nPI), y 100 ms después el resto (NG\r\n). El servidor respondió a los cinco, en orden:

+PONG\r\n+OK\r\n$12\r\ncon espacios\r\n+OK\r\n+PONG\r\n

El cliente usa el mismo parser para leer las respuestas. Como el servidor contesta en el mismo orden en que recibe, TcpClient empareja cada respuesta con su petición usando una cola FIFO de promesas (_pendientes): la primera respuesta resuelve la primera promesa.

El precio de la sencillez

Cada trozo nuevo hace un Buffer.concat y cada valor leído un slice; con mensajes enormes eso copia memoria de más. Redis usa un búfer de consulta con desplazamientos para evitarlo. Para aprender, la versión clara gana.

La vida de un comando

Estos son los diez pasos que recorre SET saludo hola desde el REPL hasta la memoria del servidor y de vuelta. Cada paso nombra el archivo donde ocurre.

  1. Tokenizar

    client.js · tokenizar() parte la línea por espacios respetando comillas: ['SET', 'saludo', 'hola'].

  2. Encolar y escribir

    TcpClient.enviar() guarda una promesa en _pendientes y escribe RespSerializer.array(tokens) en el socket: *3\r\n$3\r\nSET\r\n$6\r\nsaludo\r\n$4\r\nhola\r\n.

  3. Viajar

    TCP entrega los 35 bytes al servidor, en uno o varios trozos.

  4. Acumular

    ClientConnection recibe cada evento data y se lo pasa a su propio RespParser con feed(). Cada conexión tiene su parser y su base activa.

  5. Parsear

    El primer byte es *: _parsearArray lee tres bulk strings y el parser emite 'comando' con ['SET', 'saludo', 'hola'].

  6. Preparar

    _manejarComando pasa el nombre a mayúsculas, separa los argumentos y toma this._db, la base que esta conexión eligió con SELECT.

  7. Despachar

    CommandRegistry.execute('SET', …) encuentra SetCommand en su Map.

  8. Ejecutar

    SetCommand valida las opciones (EX, PX, NX, XX), crea new KeyEntry('hola', 'string', null), llama a store.set(0, 'saludo', entrada) y devuelve { ok: 'OK' }.

  9. Serializar

    RespSerializer.serializar({ ok: 'OK' }) produce +OK\r\n y la conexión lo escribe en el socket.

  10. Mostrar

    El parser del cliente emite { ok: 'OK' }, que resuelve la primera promesa de _pendientes; formatearRespuesta imprime OK en verde.

Almacenamiento y bases de datos

Todo el estado de Velo es un Map que contiene otros Map: una entrada por base de datos lógica y, dentro de cada una, cada clave apuntando a un KeyEntry.

// InMemoryStore
this._bases = new Map();               // 0 → Map, 1 → Map, … 15 → Map

for (let i = 0; i < this._config.DB_COUNT; i++) {
  this._bases.set(i, new Map());       // clave → KeyEntry
}

KeyEntry es la entidad del dominio: un valor, un tipo y un instante de caducidad en milisegundos (null si no caduca). El tipo hoy siempre es 'string', pero TipoDato ya declara list, hash y set. Por eso TYPE y el error WRONGTYPE ya funcionan como en Redis.

Bases por conexión

Hay 16 bases por defecto (DB_COUNT) y cada conexión empieza en la 0. La base activa es estado de la conexión, no del servidor: dos clientes pueden trabajar en bases distintas a la vez.

Aquí aparece un problema de diseño interesante. SELECT es un comando como los demás y solo recibe (store, args, db): no tiene acceso a la conexión, así que no puede cambiarla. La solución es que devuelva una intención en lugar de un efecto, { nuevoDb: 2 }, y que la infraestructura la interprete:

// ClientConnection._manejarComando
if (nombre === 'SELECT' && typeof resultado === 'object' && resultado !== null && 'nuevoDb' in resultado) {
  this._db = resultado.nuevoDb;
  this._enviar(RespSerializer.simpleString('OK'));
  return;
}

Los comandos siguen sin saber nada de sockets. El coste es un caso especial en la capa de infraestructura, y es un intercambio aceptable.

Expiración de claves

Una clave con EX, SETEX o EXPIRE guarda el instante en que muere. Velo la elimina de dos maneras, igual que Redis: cuando alguien la toca y ya ha caducado, y en un barrido periódico para las que nadie vuelve a tocar.

Perezosa: al acceder

Cada lectura pasa por InMemoryStore.get, que comprueba la caducidad antes de devolver nada. Una clave muerta se borra en ese momento y el comando ve null. KEYS y DBSIZE aplican la misma limpieza al recorrer.

get(db, key) {
  const base = this._obtenerBase(db);
  const entrada = base.get(key);

  if (!entrada) return null;

  if (entrada.isExpired()) {
    base.delete(key);
    return null;
  }

  return entrada;
}

Activa: el barrido

Sin la expiración perezosa, una clave que nadie lee ocuparía memoria para siempre. Por eso iniciarSweep() programa un setInterval que, cada SWEEP_INTERVAL_MS (1000 ms por defecto), recorre todas las bases y borra las entradas caducadas. El temporizador lleva .unref() para no impedir que el proceso termine.

Qué devuelve TTL

Tabla Respuestas de TTL, iguales a las de Redis.
RespuestaSignifica
(integer) 60Segundos que le quedan, redondeados hacia arriba.
(integer) -1La clave existe y no caduca.
(integer) -2La clave no existe o ya caducó.

INCR, DECR y APPEND conservan la caducidad de la clave; SET y MSET la reemplazan, y GETEX … PERSIST la quita.

La diferencia con Redis

Redis no recorre todas las claves. Diez veces por segundo toma una muestra de 20 claves entre las que tienen caducidad, borra las expiradas y repite si más del 25 % lo estaban. Es un algoritmo probabilístico y adaptativo que mantiene la latencia baja con millones de claves. El barrido de Velo es exacto pero cuesta O(n) por pasada, e incluye claves sin caducidad. Para un proyecto de aprendizaje es la versión fácil de verificar; para producción, la de Redis.

Configuración y línea de comandos

Cada valor se resuelve en este orden, y gana el primero que exista: la bandera de la línea de comandos, la variable de entorno, el archivo .env y, por último, el valor por defecto. El resultado se congela con Object.freeze; nadie puede cambiar la configuración en caliente.

function obtener(clave, valorDefecto, sobreescrituras) {
  if (sobreescrituras[clave] !== undefined) return String(sobreescrituras[clave]);
  if (process.env[clave] !== undefined) return process.env[clave];
  if (variablesEnv[clave] !== undefined) return variablesEnv[clave];
  return valorDefecto;
}

Cómo se leen los argumentos

cli.js es un parser de argumentos escrito a mano. Acepta --port 7000 y --port=7000, valida tipos (entero o nivel de log) y separa las opciones del comando: todo lo que va antes del primer argumento que no es una opción configura el cliente; todo lo que va después se envía tal cual al servidor. Así velo -p 7000 -n 2 keys "*" no confunde el * con nada.

$ velo --port abc
velo: la opcion --port espera un numero entero (recibido: abc)
Usa "velo --help" para ver la ayuda.      # código de salida 2

Arranque y cierre

server.js compone las piezas (configuración, almacén, registro, servidor TCP), arranca el barrido y registra manejadores de SIGINT y SIGTERM. Al cerrar, destruye las conexiones abiertas, detiene el barrido y espera a que el servidor termine. Si el puerto está ocupado, lo dice y sale.

Recarga en desarrollo

scripts/dev.js sustituye a nodemon en menos de 70 líneas. Vigila src/ con un fs.watch por carpeta, agrupa los cambios en una ventana de 200 ms y reinicia el servidor: le manda SIGTERM, espera a que salga y lanza uno nuevo con fork.

Mensajes e idiomas

Ningún texto visible está escrito en el código. Todos viven en src/i18n/es.json y en.json, y se piden por su ruta con t():

t('servidor.iniciado', { host: '127.0.0.1', puerto: 6380 })
// → "Servidor iniciado en 127.0.0.1:6380"

La función busca la clave en el idioma activo, si falta la busca en español y, si tampoco está, devuelve la propia clave, de modo que un mensaje ausente se ve pero no rompe nada. Los marcadores {nombre} se sustituyen por parámetros y los arrays se unen con saltos de línea (así está escrita la ayuda). LOCALE=es_ES.UTF-8 se reduce a es, y solo se aceptan códigos de dos letras: nunca se carga un archivo con un nombre arbitrario.

Decisiones y compromisos

Cada decisión tiene un motivo y un coste. Estos son los que dan forma a Velo.

Cero dependencias

Por qué: el objetivo es ver cómo funciona todo; una librería esconde justo lo que se quiere aprender. Por eso hay parser de RESP, de argumentos, de .env, i18n y recarga escritos a mano.

Coste: se reinventan ruedas y cada una tiene menos casos cubiertos que su versión madura.

Hablar RESP, no JSON ni HTTP

Por qué: es el protocolo de Redis, así que lo aprendido sirve para entender clientes reales; además es legible con nc y lleva longitudes que delimitan cada dato sin ambigüedad.

Coste: hay que escribir un parser con estado, en lugar de un JSON.parse.

Comandos que devuelven valores, no bytes

Por qué: si un comando devuelve null, un número o { ok }, se puede probar sin red y cambiar de protocolo sin tocarlo. El serializador es el único que conoce RESP.

Coste: casos como SELECT necesitan un canal especial ({ nuevoDb }).

Un comando por archivo y un registro

Por qué: cada comando se lee aislado, el despacho es una búsqueda en un Map y añadir uno es un archivo y una línea.

Coste: 23 archivos pequeños y algo de validación repetida.

Un solo hilo

Por qué: igual que Redis, cada comando corre completo dentro del bucle de eventos antes de que empiece el siguiente. INCR lee, suma y escribe sin que nadie pueda colarse en medio: atomicidad sin locks.

Coste: un comando lento, como KEYS * sobre muchas claves, bloquea a todos los clientes mientras dura.

Expiración perezosa más barrido completo

Por qué: la combinación garantiza que nadie lea una clave caducada y que la memoria se libere aunque nadie las lea; el barrido completo es trivial de razonar.

Coste: O(n) por pasada ().

Un binario para todo

Por qué: velo server, velo y velo get clave comparten configuración, ayuda y mensajes; Redis lo reparte entre redis-server y redis-cli.

Coste: el parser de argumentos tiene que distinguir modos.

Puerto 6380

Por qué: no choca con un Redis local en el 6379, así que se pueden comparar los dos lado a lado.

Diferencias con Redis

Velo imita la superficie de Redis, no su escala. Esta tabla separa lo que se comporta igual de lo que no.
